- 実行: bun apps/cli/src/run.ts --profile headless --patch .tmp/sessions.yml --model ollama-cloud/deepseek-v4.1-flash --json "Reply with the single word pong"
- 終了コード: 0（stderr は空）
- セッションログ（.tmp/sessions-ws/<id>/session.v1.jsonl）: session/header → agent/inbox/queued → turn/start → agent/inbox/claimed → step/start → system/message → user/message → request/header（provider=ollama-cloud, model=deepseek-v4.1-flash）→ assistant/message（本文は pong）→ step/end → turn/end（reason は { kind: completed }）

## 2026-10-14 の追記（dsh との差を埋めた分）

`docs/notes/2026-10-14-dsh-gap-backlog.md` の全項目を実装・検証した。スライスの対応は次のとおり。

- S2 Safety: sandbox の既定が `seatbelt` になり、無制限は `sandbox: none` の明示になった。書き込みは cwd と一時ディレクトリに限られ、`sandbox-exec` が使えない platform では起動が失敗する。承認は answerer 不在・例外を拒否に正規化し、永久に待たない（待つのは `listen()` した相手がいるときだけ）。
- S3 Tier 0: パス解決は `workspace.ts` の 1 本になり、workspace の外とリンク経由の書き込みを拒否する。
- S4 Tier 1: spill の CLI 既定は 32KB（profile の `maxSpillBytes` で変える）。
- S5/S6: `team`（roster と board）、`schedule`、`goal`、`workflow`、`plugin`、コマンド（`/help` / `/status`）、subagent の route / fresh / idle が入った。
- S1/S8: セッションの一覧と読み戻しは CLI（`jzh sessions`）が持ち、会話 view は TUI と Web で同じもの（`@jozo-harness/ui-view`）を読む。tool の 1 行要約は pipeline が描いて `tool/call` / `tool/result` の `summary` に記録する。
- 検証機構: `apps/cli/tests/snapshot.test.ts` が出荷構成のまま記録を再生し、正規化したログと workspace を `apps/cli/tests/snapshots/` と比べる（記録を更新するのは `UPDATE_SNAPSHOTS=1 bun test snapshot`）。
- 未確認は各項目の追記と [backlog](2026-10-14-dsh-gap-backlog.md) の「未確認」節にある。dsh 側で確かめられないものは保留のままで、判定できていないことを「済み」とは書いていない。

## 秘密情報の扱い（2026-10-13 決定）

- 保存は平文の secrets.env（XDG_CONFIG_HOME/jzh/secrets.env、無ければ ~/.config/jzh/secrets.env）、モード 600。グループや他人が読める場合は警告する。
- 入力は jzh auth add PROVIDER（サービス名で指定。ollama / openai を表に持つ）と jzh auth set ENV_NAME。端末では打鍵を隠し、パイプでも渡せる。list は名前だけ、remove で削除。
- 読み込みは起動時。シェル環境が最優先、次に cwd 祖先の .env（近いものが外側を上書き）、次に secrets.env（空いているキーだけを埋める）。
- 暗号化はしない。理由: 実行時に平文の鍵が必要で、復号のパスフレーズも同じ環境に置くことになり守れる範囲が狭い。パスフレーズを忘れると鍵を失う確実なリスクと、毎回の入力や起動のコストを足す。守るべき「ログに鍵を出さない」は実測で確認済み（ダミーキーで 401 を起こし、セッション JSONL と stdout、stderr を grep して一致なし。鍵は Authorization ヘッダと検索 provider にのみ渡る）。
- 将来「保管時の保護」が必要になったら、パスフレーズではなく OS キーチェーン（macOS の security など）にマスターキーを預ける形にする。パスフレーズ方式の実装は一度書いたが未使用のため削除した（履歴には残っている）。
